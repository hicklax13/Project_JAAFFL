## CBS integration and compliance

**Restatement.** The tool must connect to a live CBS fantasy football league and its draft room, read league settings and draft state in real time, detect draft order and roster rules, and keep working as picks happen. The practical constraint is that this has to happen against CBS’s current web and app experience, not against a clearly published modern public developer platform. CBS’s current product clearly supports live drafting, league settings, standings, draft results, projections, rankings, injury updates, and commissioner customization, so the product requirement is feasible from a user-experience standpoint. citeturn21view0turn21view1turn21view2

The first technical conclusion is that CBS integration is the hardest and most fragile requirement. I found an old first-party CBS “Fantasy Open Platform” presentation from 2012 describing OAuth-style access tokens, REST endpoints, league settings, teams, standings, transactions, player updates, and JSON/XML responses. But I did not find a current public first-party CBS developer portal or current API reference for fantasy football. Community-maintained projects explicitly describe the CBS fantasy API as “deprecated but still available,” and recent discussion indicates CBS login changes made token automation more brittle. That combination means the integration surface probably still exists in some form, but it should be treated as **CONFLICTING/STALE RISK**, not as a dependable modern public API. citeturn2view3turn1search1turn14search4

The second technical conclusion is that legal and platform risk matter as much as code risk. CBS’s general terms say users may access content only for personal, non-commercial purposes unless otherwise authorized in writing, and CBS’s acceptable-use section prohibits unauthorized spidering, scraping, data mining, harvesting, or other unauthorized automated means. CBS also reserves the right to change or discontinue features and to restrict or terminate access. For a personal-use tool this is already a caution; for a commercial product it is a major architecture constraint. citeturn4view0turn5view0turn2view0

That creates three realistic integration approaches. The first approach is a **browser extension running in the user’s own authenticated CBS session**. This is technically attractive because content scripts can read and modify page content when host permissions are granted, the cookies API can access site cookies when both cookie and host permissions are granted, and `chrome.webRequest` can observe and analyze network traffic. This is also how third-party CBS sync products appear to solve adjacent problems: League Legacy markets a CBS Chrome extension for imports, Fantasy Life markets CBS league sync, and DraftKick’s public write-up argues that a Chrome extension is the smoothest pattern when a fantasy site lacks a reliable public API. citeturn6search3turn26search0turn6search0turn2view4turn25view0turn25view1

The browser-extension approach has two strong advantages. First, it avoids standing up a server-side credential harvester, because the extension works inside the user’s existing authenticated session. Second, it can read live draft-room state directly from the page, intercepted requests, or framework state, which is usually more current than league pages that lag during a draft. Its main weaknesses are fragility, the need for careful permission scoping, browser-specific maintenance, and continued CBS terms-of-use exposure. Because CBS’s app and web client are actively updated, DOM and request patterns can change without warning. citeturn25view1turn26search1turn26search3turn21view0

The second approach is **headless browser automation**, usually with Playwright. This is feasible because Playwright can inspect page network activity, emit page-level WebSocket events, and even route WebSocket connections for deeper control. In practice, that lets a controlled browser session watch the live draft room and mirror pick events into your backend. The weakness is that this is heavier, easier for CBS to break, worse for user trust, and more operationally expensive than an extension. It is a stronger fit for internal testing and regression monitoring than for the production MVP. citeturn6search2turn6search6turn6search17

The third approach is **unofficial or deprecated API access** via token extraction. The historical CBS platform docs make clear that league settings, teams, stats, transactions, and player updates were part of the intended API model, and community packages still exist for token fetching and league extraction. But because that path appears deprecated and login automation is reportedly less stable now, it should be treated as a best-effort fallback rather than the product backbone. citeturn2view3turn14search0turn14search1

A separate design implication is draft-order detection. CBS commissioner leagues support extensive customization of draft, schedule, and scoring, and CBS help indicates manual/custom draft-order behavior is supported. That means your tool should never assume a simple snake based on league size alone. It should read the actual draft board or draft metadata from the live room and only fall back to inference if the explicit order is unavailable. citeturn21view2turn16search1

**Section recommendation.** For the MVP, the best architecture is a **Manifest V3 Chrome extension + local companion service**. Let the extension run only on CBS draft and league pages, extract league settings and live pick events from the authenticated browser context, and stream normalized events to a localhost backend. Keep Playwright for testing and emergency recovery, and keep any unofficial CBS API adapter behind an interface that can be disabled at runtime. Do **not** build a commercial product that depends solely on CBS scraping or personal-use content rights. citeturn26search15turn6search1turn25view1turn5view0turn4view0

## NFL and fantasy data stack

**Restatement.** The tool must ingest NFL player stats, NFL team stats, injuries, rankings, projections, draft data, and historical league behavior from 2023 to the present, while also supporting future-looking 2026 and 2027 recommendations. That means the data layer must combine four different categories: league-specific CBS data, open NFL performance data, fantasy ranking/projection data, and current injury/news data. citeturn21view0turn21view1turn20view0

The best free/open foundation for historical football performance is **nflverse/nflfastR/nfl_data_py**. nfl_data_py exposes play-by-play, weekly data, seasonal data, rosters, schedules, draft picks, and ID mappings, while nflfastR publishes play-by-play since 1999 and models for expected points and win probability. For your use case, that gives you deep historical player and team form, opponent strength features, usage trends, and backtesting material at low cost. citeturn7search4turn19search3turn19search13

Open data is not sufficient for everything, because the current injury picture is fragmented. The official NFL site publishes current injury reports and current stats, and CBS itself publishes a current injury report. But nflverse explicitly states its prior injury source died after the 2024 season, leaving no 2025 injury data and no ETA for restoration. That is an important **VERIFIED GAP**: if you want live or recent injuries, a free-stack-only design will be incomplete. citeturn7search2turn22search16turn7search14turn7search8

That pushes the data strategy toward a tiered model. The first tier is the **free/open historical layer**: nflverse for play-by-play, weekly and season stats, rosters, schedules, and draft picks; official NFL/CBS pages for current browsing and validation; and CBS league-state extraction for custom scoring, roster slots, transaction settings, and historical league records. CBS markets robust league history, and its commissioner FAQ says renewal preserves rosters, rules, and scoring; third-party sync/import products for CBS history exist as well. That means extracting manager tendencies, prior draft behavior, and team-history features is realistic if you capture yearly snapshots into your own datastore. citeturn7search4turn21view2turn21view3turn2view4turn25view0

The second tier is the **low-cost premium fantasy layer**. FantasyPros now has an official API with consensus rankings, ADP, player metadata, projections, news, injuries, and player points. Its public pricing says prototyping is free, while Premium access is bundled with MVP/HOF from $5.99 per month for personal, non-commercial apps; commercial usage requires a separate commercial plan. This is the cleanest low-cost way to add expert consensus, practice-report-style injury context, and current fantasy-specific ranking data to a personal-use assistant. citeturn20view0turn9view1

The third tier is the **commercial real-time vendor layer**. SportsDataIO markets projections, points, fantasy metrics, news/images, depth-chart coverage, and historical data, and its fantasy page says its BAKER engine supports season-long, rest-of-season, partial-season, and dynasty-career projections. Sportradar’s NFL docs show a large REST API with historical and real-time options plus Push feeds for real-time customers, and its weekly injuries endpoint documents a 120-second cache window. These are much better fits for a commercial or multi-user product than individual-site scraping and personal-use fantasy APIs. citeturn9view3turn23view0turn9view5turn9view6turn23view1

For advanced team and player features, the official **Next Gen Stats** ecosystem matters. NFL Football Operations states that Next Gen Stats captures classification and advanced tracking outputs such as completion probability, expected rushing yards, and win probability, and the main NGS site emphasizes real-time location, speed, and acceleration tracking. Those fields are useful for role-adjusted player efficiency features and for detecting fragile profiles that box-score-only projections miss. citeturn7search1turn7search5turn22search5

The 2026–2027 requirement needs one important separation. **VERIFIED 2026 projections** are available from vendors like FantasyPros and SportsDataIO. **Explicit 2027 statline projections** are much less clearly available in public docs. FantasyPros documents weekly, preseason, and rest-of-season projections, while SportsDataIO publicly markets dynasty-career projections rather than year-labelled 2027 NFL statlines. So the practical answer is: use verified 2026 vendor projections, and generate **ESTIMATED 2027** values internally from your own aging, role, and injury-survival model unless and until you license a vendor feed that explicitly publishes forward-year statlines. citeturn20view0turn9view3

The storage architecture also needs two modes. For a single-user or self-hosted build, **DuckDB + Parquet + SQLite** is the cheapest strong option: DuckDB is an in-process OLAP database optimized for analytical query processing, and SQLite offers a zero-admin local store with JSON support. For a multi-user hosted system, **PostgreSQL + Redis Streams + DuckDB** is stronger: PostgreSQL `jsonb` is efficient for semi-structured league settings and extracted CBS payloads, Redis Streams are suited for append-only real-time event logs and consumer groups, and DuckDB remains excellent for local research notebooks and backtests. citeturn18search8turn18search11turn18search1turn18search2

**Section recommendation.** Use a **hybrid stack**. Make nflverse and official NFL/CBS pages the historical and validation base, add FantasyPros as the lowest-cost structured fantasy API for personal use, and reserve SportsDataIO or Sportradar for any commercial or multi-user launch. Persist all CBS league snapshots locally from the first day of use so the system can build its own long-term manager-tendency dataset instead of depending on CBS history always remaining accessible. citeturn7search4turn20view0turn23view0turn9view5

## Draft optimization engine

**Restatement.** The recommendation engine must convert all of the above data into live pick-by-pick draft advice that maximizes season value and, ideally, expected playoff or title odds under the exact CBS league settings. That makes this a constrained optimization and simulation problem, not just a rankings display problem. citeturn21view2turn20view0

The strongest foundation is still **league-specific value over replacement/value-based drafting**, because it directly ties player value to roster slots, starting requirements, bench depth, and waiver baselines. FantasyPros’ VBD explanation emphasizes calculating value over a replacement-level player defined by league size and roster settings, and public draft-assistant implementations such as `ffdraft.app` explicitly describe using projections plus value-over-replacement estimates to optimize roster construction. That matters because a raw consensus rank does not encode roster scarcity in a custom CBS league. citeturn19search14turn14search11

Pure VORP, however, is not enough for a live room. It does not model what your opponents are likely to do or how the draft board will evolve. The engine therefore needs a second layer: **opponent pick-probability modeling**. Use ADP and expert-consensus signals from FantasyPros, plus CBS market data available on the site itself, plus manager-specific historical tendencies from prior CBS drafts. The result should be a probability distribution over the next several picks, not a single deterministic guess. citeturn20view0turn16search2turn25view0

Once you have replacement values and opponent pick probabilities, the live recommendation problem becomes: “Which available player maximizes the expected quality of all feasible final rosters after the rest of the room makes probabilistic picks?” That is where Monte Carlo draft simulation plus constrained roster optimization is appropriate. OR-Tools’ CP-SAT solver is built for arbitrary constrained optimization over integers, which is a good fit for roster-slot, position-cap, stack, and contingency constraints. In parallel, XGBoost is a strong fit for residual modeling such as opponent tendencies, breakout probability, and projection error correction, and Optuna is a practical tuning layer if you decide to optimize those models systematically. citeturn11search4turn11search0turn11search1turn11search17turn11search6

The most robust quantitative design is therefore a four-stage engine. Stage one is a **projection ensemble** that combines vendor fantasy projections, nflverse historical production, official advanced metrics, injury status, and team-context features. Stage two is a **league translation layer** that converts projected statlines into exact CBS league scoring, derives replacement baselines, and computes positional scarcity. Stage three is an **opponent model** that estimates pick timing from ADP, ECR dispersion, and manager history. Stage four is a **draft simulator and roster optimizer** that measures each candidate pick by expected end-state roster value and expected season-level outcomes. citeturn20view0turn7search5turn19search2turn11search4

If you want the engine to optimize for “win probability maximization” instead of just projected points, you can extend the final objective from expected fantasy points to **season simulation outputs** such as expected weekly wins, playoff odds, and title odds. That is conceptually consistent with the way CBS itself advertises 10,000-season simulation in SportsLine fantasy content, and with nflfastR’s open win-probability modeling approach. In practice, your fantasy version would simulate weekly outcomes from projected distributions rather than optimizing only on point totals. citeturn15search19turn19search2turn19search3

The key modeling choice is what **not** to do first. An end-to-end reinforcement-learning draft agent sounds sophisticated, but it needs huge amounts of platform-specific historical draft-room state and reward labels. You do not have that initially, especially on CBS. A structured optimizer built on transparent projections, manager models, and simulation will be more auditable, easier to debug, and easier to adapt when scoring settings change. citeturn21view2turn20view0turn11search4

**Section recommendation.** Build the engine in this order: exact CBS scoring parser, projection ensemble, league-specific replacement-value model, opponent pick-probability model, then Monte Carlo + CP-SAT roster optimization. Make the live recommendation score a blend of projected season points, replacement-adjusted scarcity, injury-adjusted availability, and simulated playoff odds. Treat 2027 outputs as explicitly **ESTIMATED** model outputs rather than vendor-verified projections unless you license a forward-looking commercial feed. citeturn21view2turn20view0turn11search4turn9view3

## UI, real-time workflow, and AI assistant

**Restatement.** The UI has to be professional, convenient, interactive, and fast enough to support a live draft. It also needs a context-aware AI popup that can search the web, search internal data, explain recommendations, and react to what the user is looking at. That means the UI stack must prioritize latency, data density, and low-friction interaction more than conventional marketing polish. citeturn21view0turn13search12

There are two serious UI architectures. The first is a **browser-overlay model**: a Chrome extension injects an overlay panel directly into the CBS draft room. This is compelling because content scripts can access and modify page content, and script injection with host permissions is supported in MV3. It minimizes context switching and lets the user see recommendations beside the live draft board. The downside is tighter coupling to CBS layout changes and more complexity in keeping extension UI isolated from page styles and scripts. citeturn26search3turn26search15

The second is a **separate web app/dashboard** fed by the extension or local backend. This is better for rich visual analytics, multi-panel layouts, and long-lived state. Next.js supports streaming and progressive rendering, which helps with data-intensive dashboards. For visualization, Apache ECharts is unusually strong for a fantasy analytics tool because it supports a wide chart catalog, progressive rendering, and stream loading over WebSocket. For dense tables, AG Grid Community is free and feature-rich, while TanStack Table + TanStack Virtual is a better choice when you want maximal customization and 60 FPS virtualization. citeturn24search0turn24search4turn12search3turn12search0turn12search7turn12search19turn12search2turn12search20

For your use case, the highest-quality product is actually a **hybrid**: keep a thin in-page overlay for urgent in-draft guidance and a richer external dashboard for deeper analysis. The overlay should show recommended pick, tier breaks, likely snipes before next turn, positional run risk, and quick-chat access. The external dashboard should show board state, projection distributions, manager tendency panels, injury/news tape, and scenario comparison tools. That separation reduces clutter without sacrificing speed. citeturn12search3turn12search7turn25view1

For the AI assistant, the guidance is much clearer today than it was a year ago. OpenAI’s Responses API now supports built-in web search, file search, and function calling, and the platform guidance explicitly frames it as the main interface for stateful interactions with tool use. File search is designed for uploaded knowledge bases, web search can be enabled as a built-in tool, and function calling is the mechanism for your own database and league-specific tools. OpenAI’s older Assistants API is deprecated and scheduled to shut down on August 26, 2026, so there is no reason to build new work here on Assistants. citeturn13search12turn13search0turn13search3turn13search2turn13search14

For live voice, OpenAI’s released Realtime API is the right current interface, not the removed beta. That said, if your priority is lowest cost, a text-first popup is much better. OpenAI’s pricing page shows the text modality on realtime models is materially cheaper than continuous audio, and the broader product docs say Realtime is best for live audio while the Responses API is the main interface for tool-rich generation. The result is straightforward: default to text chat in the draft room, and make voice optional. citeturn29search6turn29search1turn13search1turn13search12

There is also a Python-first alternative for faster internal prototyping: **Dash** or **Streamlit**. Streamlit is extremely fast to prototype with, and Dash remains a strong Python framework for interactive data apps; Dash AG Grid is the current advised path for rich Python data grids. But a heavily polished, extension-integrated, low-latency live-draft product will usually outgrow Streamlit faster than it outgrows React, and Dash trades some frontend flexibility for Python convenience. citeturn27search1turn28search6turn28search1turn28search4

**Section recommendation.** Use **React/Next.js for the main product**, with **AG Grid Community + ECharts + TanStack Virtual** for the analytics surface. Pair it with a **minimal CBS-page overlay extension** for in-draft prompts. Build the AI assistant on the **Responses API** with function tools for your data store, file search for saved rules/docs, and optional web search for breaking news. Make voice a later, optional add-on through Realtime rather than an MVP requirement. citeturn24search0turn12search7turn12search3turn12search20turn13search12turn13search6turn29search1

## Cost, licensing, and deployment strategy

**Restatement.** The solution should be no-cost or lowest-cost wherever possible, but it still has to handle live draft syncing, projections, injuries, and AI. The right answer therefore depends on whether the tool is purely personal or is meant to become a shareable/commercial product. citeturn20view0turn5view0

For a **personal-use build**, the cheapest viable stack is strong. CBS free fantasy is free, while Commissioner leagues cost $179.99 for up to 30 teams and support extensive customization. FantasyPros offers a free prototype tier and a $5.99 per month Premium path for personal, non-commercial production apps. On the infrastructure side, a local extension plus local backend plus DuckDB/SQLite can run at effectively zero recurring cloud cost. This is the best value path if the user is the only operator. citeturn21view2turn20view0turn18search8turn18search11

For a **commercial or shared product**, the cost math changes because the license math changes. CBS terms restrict commercial exploitation and unauthorized scraping, and FantasyPros’ low-cost Premium tier is explicitly for personal and non-commercial apps. That means a commercial launch should assume licensed fantasy data from FantasyPros Commercial, SportsDataIO, Sportradar, or a similar vendor, with CBS used only as a user-authorized source of league-specific state and settings rather than as an unlicensed data backbone. citeturn5view0turn4view0turn20view0turn23view1turn23view0

If you do want a small hosted footprint, Supabase has a free plan and a Pro starting at $25 per month, while SportsDataIO and Sportradar both offer free trials but not simple public self-serve production pricing for the premium real-time packages most relevant here. That is another reason the MVP should be local-first: it delays cloud and vendor spend until you prove the draft-sync and recommendation loop. citeturn24search1turn23view0turn23view1

**Section recommendation.** Split the roadmap into two explicit tracks. The **personal research tool** should stay local-first, use CBS browser sync, nflverse, and FantasyPros Premium, and avoid paid cloud wherever possible. The **commercializable platform** should be designed from day one to swap in licensed real-time providers and to limit CBS dependence to user-authorized league-state extraction. That separation preserves both cost discipline and legal clarity. citeturn20view0turn5view0turn23view0turn23view1

## Final implementation roadmap

Build the MVP in seven dependencies-first stages.

1. **Create the CBS sync layer.** Build a Manifest V3 extension that runs only on CBS fantasy league and draft pages, reads league metadata and live draft events, and emits normalized draft events to localhost. Use content scripts for DOM/state extraction, `webRequest` for traffic observation, and the cookies API only if absolutely necessary. citeturn6search0turn6search3turn26search0turn26search15

2. **Normalize league settings.** Parse CBS roster slots, flex eligibility, scoring rules, team count, keeper/dynasty flags if present, and draft order from live room or settings pages. Persist every league snapshot so historical analysis is built inside your own datastore. citeturn21view2turn16search1turn21view3

3. **Stand up the data warehouse.** Start with DuckDB + Parquet + SQLite for local work; define stable player/team/league IDs and crosswalks for CBS, NFL, FantasyPros, and nflverse. If you later go multi-user, graduate to PostgreSQL `jsonb` and Redis Streams without changing the domain schema. citeturn18search8turn18search11turn18search1turn18search2

4. **Add the external data tiers.** Ingest nflverse/nflfastR historical stats first, then add FantasyPros for rankings, projections, ADP, news, and injuries. Keep a plug-in interface ready for SportsDataIO or Sportradar if you need commercial-grade real-time injuries or broader licensing. citeturn7search4turn19search3turn20view0turn9view5turn23view0

5. **Ship a transparent draft engine before a complex one.** Version one should compute exact CBS scoring translations, positional replacement values, tier breaks, opponent-pick probabilities, and Monte Carlo end-of-draft roster values. Only after that is stable should you add XGBoost residual models, calibrated injury-risk adjustments, and 2027 aging curves. citeturn19search14turn11search4turn11search1

6. **Build the two-surface UI.** Add a thin in-page overlay for “best pick / next-turn risk / why” and a richer Next.js dashboard for board analytics, manager tendencies, and scenario comparison. Use AG Grid Community for board and roster tables and ECharts for distribution, trend, and scenario visuals. citeturn24search0turn12search7turn12search19turn12search3

7. **Integrate the AI assistant last, but wire for it early.** Expose database queries, league-state summaries, and news lookups as typed function tools; use Responses API file search for uploaded rules or exports; optionally add web search for breaking news. Keep voice optional through Realtime after the text assistant is stable. citeturn13search12turn13search2turn13search0turn13search3turn13search1

## Executive Summary

The most important finding is that this product is technically feasible, but **CBS integration is the gating risk**. CBS clearly supports live draft rooms, commissioner customization, league history, rankings, projections, and injury/news features, but I did not find a current public fantasy developer platform. The only first-party API evidence I found is older platform documentation, while community tooling describes the fantasy API as deprecated and brittle after login changes. CBS terms also prohibit unauthorized scraping and commercial exploitation without authorization. citeturn21view0turn21view1turn21view2turn2view3turn1search1turn5view0turn4view0

Because of that, the best MVP architecture is **local-first and extension-based**. A Chrome extension running in the user’s authenticated CBS session should capture league settings and live draft events, then feed a localhost backend that combines CBS state with nflverse historical data and a low-cost fantasy API such as FantasyPros. This is the lowest-cost path that still supports real-time recommendations. citeturn25view1turn26search0turn6search3turn7search4turn20view0

For the decision engine, the right starting point is **not** a black-box AI drafter. It is a transparent stack: exact CBS scoring parser, replacement-value model, opponent pick-probability model using ADP and manager history, then Monte Carlo simulation with constrained roster optimization. That gets you auditable live recommendations and a clean upgrade path into more advanced predictive modeling. citeturn19search14turn14search11turn11search4turn20view0

For the UI and assistant, the strongest product design is a **hybrid overlay + companion dashboard**. Use an injected overlay for urgent recommendations in the live draft room, and a separate Next.js analytics surface for deeper board and roster analysis. Build the assistant on the Responses API with function calling, file search, and optional web search; keep voice optional because realtime audio is materially more expensive than text. citeturn24search0turn12search3turn12search7turn13search12turn13search2turn13search0turn13search3turn29search1

The commercial conclusion is also clear. A **personal-use tool** can be built cheaply with CBS sync, nflverse, and FantasyPros Premium. A **commercial product** should not rely on CBS scraping or personal-use fantasy licenses; it should assume licensed feeds from providers such as FantasyPros Commercial, SportsDataIO, or Sportradar, with CBS used mainly for user-authorized league-state extraction. citeturn20view0turn23view0turn23view1turn5view0turn4view0
